## Inventory and decision

Resolving this with the repository state verified on 2026-09-30. **No runtime behaviour changes are proposed** — the outcome is that every transaction boundary stays on PostgreSQL default `READ COMMITTED`, and this issue's own acceptance criteria for the pilot are satisfied by the non-goal.

### Baseline

- PostgreSQL default `READ COMMITTED` on every write path.
- `rg -n "40001|40P01|isolationLevel" packages apps scripts` returns **no matches** — no code passes `isolationLevel`, and no runtime path handles a serialization failure because none can currently occur.
- Eight `.transaction(` call sites in the whole repository, listed in the table below. Everything else that looks like a concurrent flow is a single atomic statement, which is the cheapest correct form.

Two flows that are *not* transactions are recorded here because they are the ones that carry a durable lease, and they are the shape a reader might mistake for a transaction:

- Scheduled-report claim and study-reminder claim are single-statement `INSERT … ON CONFLICT DO UPDATE … WHERE status = 'released'` / `WHERE status IN ('pending','failed')` with a fresh `lease_token`. Correct under `READ COMMITTED` with no row lock; the CAS and the write are one statement (`packages/scheduler-core/src/adapters/platform-report-claim.repository.ts:200`, `packages/study-reminder-shared/src/infrastructure/typeorm-study-reminder-job.repository.ts:338`).
- Webhook inbox claim is the same shape. `listDue()` is a plain `SELECT … ORDER BY id LIMIT n` with no `SKIP LOCKED`, so two workers may read the same row and only one wins the CAS — a wasted read, not a correctness problem. `SKIP LOCKED` remains the upgrade path only if claim contention shows up in metrics.

### Why nothing is a candidate for elevated isolation

- Every invariant above is either single-row or expressible as one conditional statement. A higher isolation level only pays for itself when a multi-row invariant cannot be written as a constraint or a single-statement guard; there is no such invariant here.
- The one genuinely multi-row operation is privacy delete (flow 7), and it is a *set of deletes in one transaction* — raising isolation would not change its outcome, it would only add serialization-failure handling to a path that must not be retried.
- `40001` is unreachable at this baseline. Handling it would be speculative code for a condition the code cannot produce.

### Global/session isolation risk analysis

Recorded so the question is answered rather than deferred:

- **PgBouncer is `pool_mode=session`**, deliberately, because advisory locks are session-scoped. A serialization failure inside a transaction consumes the session and forces a retry; at 20 server-side slots and three apps, retry amplification lands directly on pool exhaustion rather than on the individual bot.
- **All eight boundaries run more than one statement.** Global `SERIALIZABLE` would therefore make essentially every write path retry-capable, adding a retry layer to paths that are already lease-guarded and idempotent.
- **Advisory locks are unaffected by isolation level**, so the existing cross-pod exclusion would not improve; only the failure surface grows.
- **The migration runner holds `MIGRATION_LOCK_ID` on a dedicated session** and would need an explicit exemption, as #688 already requires for timeouts.
- Net: a global change buys no new invariant and adds retry pressure to every write path. Recommendation is to keep `READ COMMITTED` and revisit only with a named invariant.

### Consequences for the downstream chain

- **#805 (pilot)** should be closed as **not-needed** with this inventory as the evidence — its own acceptance criteria already provide for that outcome: *"If no candidate is justified, the issue is resolved with the decision evidence and no runtime change."* Implementing a pilot here would mean inventing an invariant to justify it.
- **#806 (global/session evaluation)** should be closed as not-needed on the same evidence: there is no credible reason to evaluate a global change, which is the condition #806 itself sets before it may run.
- **#807 (observability/runbooks)** is unaffected and remains valid — the deadlock signal and lock-wait observability it covers are real gaps regardless of isolation level, and #688 plus #1476 already own them.
- ADR-0008 already records the mechanism table and the "do not raise isolation globally" rule; this inventory is the per-flow detail ADR-0008 points at rather than duplicates. #1481 carries the same baseline statement into `.claude/rules/database.md` where an implementer will meet it.
