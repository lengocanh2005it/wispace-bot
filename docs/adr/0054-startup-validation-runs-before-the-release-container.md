# Startup validation runs before the release container, not through the DI graph

**Status: accepted**

Configuration that the application refuses to start on is configuration **staleness**: a stored value that was valid when it was written and stopped satisfying a code constraint afterwards. Nothing detects it until the value is evaluated, so it survives across deploys and surfaces as a deploy that starts a container, watches it crash-loop, burns the 4-minute health budget, rolls back, and repeats on the next cron tick. Two real instances: `REPORT_SEND_CONCURRENCY=5` against a background admission capacity of 3 (#1363), and an OpenRouter credential in the shared OpenAI key slot (#1075).

After the image pull and **before the new container exists**, `vps-deploy.sh` runs `node apps/$APP_NAME/dist/config-validation.js` in the release image via `docker run --rm`, using the same `--env-file` and the same hardening flags as the release container, and gated only by the monitoring network. It logs into Vault with the bootstrap AppRole — the values being checked are Vault-delivered and absent from the Docker bootstrap environment — then reports every offending key in one pass and exits non-zero. Nothing is started, no migration runs, nginx keeps routing to the live container, and the failure costs seconds rather than minutes.

The validator **re-invokes the same shared constraint functions the application enforces** — `validateInternalApiKeyEnv`, `getPostgresSsl`, `createLlmProviderAdapterFromEnv`, `buildLlmExecutionConfig`, `resolveBackgroundProducerConcurrency` — rather than booting Nest to discover them. Each app's `config-validation.ts` is configuration only: it names its Vault application and its producer list, and delegates the Vault load, the reporting and the exit code to `createStartupValidationRunner` in `@wispace/bot-common/config`. Producer descriptors are exported next to the report crons and imported by the validator, so the phase and the running process cannot disagree about a producer name or an env key; a per-app inventory spec fails when a `*_SEND_CONCURRENCY` key is read anywhere in an app without a matching probe.

## Considered options

- **Boot the DI graph to discover the constraints:** rejected. `preview: true` instantiates nothing — `injector.js` short-circuits before every constructor and `useFactory`, and `initOnPreview` has no user-land decorator — so it would exit 0 against a broken environment. `createApplicationContext` does instantiate, but it requires live Postgres and Redis, mounts all 28 `@Cron` jobs, and starts a second `RedisChatQueueWorkerService` against the shared queue while the old container is still serving, which can send real learner messages during a validation run. A gate that can emit messages is worse than no gate.
- **Re-declare the constraints in a hand-written script with no shared functions:** rejected. A second copy of the rules is the mechanism by which the stale value survived in the first place.
- **Keep the constraints in the shared packages and accept a second copy in each app's validator:** rejected. Sharing the constraint functions removes the duplication of *behaviour*; what remains duplicated is the *list* of probes, and the inventory spec is what holds that list.
- **Run the phase after the health check, reusing the existing pre-cutover slot:** rejected. The application exits before it can serve `/health/ready`, so that slot is unreachable for exactly the failures this exists to catch.
- **Fold the checks into the existing `MIGRATION_PREFLIGHT_CMD`:** rejected. That command is a pre-migration `pg_dump` plus a writer-primary assertion, and `preflight` already names it. The name **startup validation** keeps the two apart.
- **Extend the phase to every boot-time refusal:** partially adopted, with the remainder named per check rather than as a blanket. Not covered: `CHAT_HISTORY_STORE` (needs a live Redis probe); the WISPACE upstream URL policy and `CHAT_QUEUE_STORE=redis` (each needs a per-app URL/config list, or a package whose root export would pull the whole agent surface into a deliberately lean validation run — duplicating the resolver's logic instead would reintroduce the drift this design removes); `CHAT_BURST_STORE`, `MESSENGER_APP_SECRET` and `MESSENGER_WEBHOOK_SIGNATURE_VERIFY` (Messenger-only, each behind a strict-production gate that would have to be re-derived here, which is a second copy of the condition rather than of the constraint). All of them remain enforced by startup itself. This is a known gap against the issue's first acceptance criterion, and it is stated here rather than implied: the criterion is met for the two instances the issue names plus the shared constraints above, not for every refusal the application enforces.
- **Report warning-class rules as violations:** rejected. `LLM_EXECUTION_ENABLED=false` warns and boots, so the validator mirrors it rather than reporting a refused start.
